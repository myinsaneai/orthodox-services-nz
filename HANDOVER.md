## 2. How we work (please keep doing this)
1. The assistant builds changes in a clone of the repo, runs `npm test`, the build and `npm audit`, and delivers a **zip of only the changed files** plus a short summary.
2. The developer unzips over the project (overwriting), runs `npm install` if `package.json` changed, then `npm test`, deploys (`firebase deploy --only ...`), tests on a phone, then commits and pushes.
3. The assistant then **verifies the pushed commit on a fresh `git clone`**: files identical to what was sent, clean `npm ci`, build, tests, audit, no secrets tracked.
4. Style: concise English, plain words, commands for **PowerShell**, at most one question per reply, state assumptions instead of asking when a sensible default exists. Mention anything not verified live (rules, sign-in, deploys).
5. When something "doesn't change", check the file on disk (`Select-String -Path ... -Pattern ...`) before debugging; a zip unzipped into the wrong folder was the usual cause in the sister project.
6. The assistant does not commit for the developer: it leaves the changes in the working tree and delivers the zip.

**Saving tokens in a new session:** do not print or rewrite whole files. Use `git clone`, `grep`, and small targeted edits (Python `str.replace` with an assert that the old text exists). Re-use the test patterns already in `tests/`. Do not repeat the README back.

## 6. Decisions already made
- **Design:** Option A. Options B (directory-first, light header), C (ornamented, stripe divider) and D (true meander divider) were mocked up and not used; do not bring them back without being asked. Header seals are 100 px (56 px on phones), taken from a 232 px source for sharpness.
- **Menu:** exactly Services, Parishes, About plus the language switch. A test enforces the three items.
- **Responsive layout:** under 900 px everything is centred in a 700 px column. From 900 px the header is left-aligned as one group (seal, title and menu, seal; the title block does not grow, so the second seal stays next to the title and is not pushed to the right edge), headings and content start at the left page edge and use the full width; services and parishes are auto-fill card grids (minimum card width 340 px, parishes 280 px). The title/menu therefore start after the left seal (about 164 px in) while headings start at the page edge (40 px); changing that is a one-line CSS decision. Layout lives in CSS classes because inline styles cannot do media queries.
- **One design for all parishes**, with only a small per-parish accent (`accentColor`: the coloured bar on a service card and the dot in the directory). No per-parish themes, no theme switcher (unlike the Russian site's `themes/`).
- **Roles (from 23 Nov 2026, Firestore-only; no Cloud Functions):** `user`, `coordinator`, `admin`, `superadmin`, stored as `users/{uid}.role`. Everybody who signs in gets a profile (`users/{uid}`, created by the client with role `user`; `parishIds` is `[]`). `user`: saves favourite parishes and applies to become a coordinator (not built yet). `coordinator`: edits services of the parishes in their own `parishIds` (set to `[]` for every other role). `admin`: edits every parish's services; gives the roles user / coordinator / admin, **only to people who are currently user or coordinator** (cannot touch other admins or make a superadmin). `superadmin`: everything, plus any role for anybody, deleting profiles; parishes, groups and settings are superadmin-only. Nobody can change or delete themselves. The same table is in `src/lib/roles.ts` (tested) and `firestore.rules` (static tests only, see section 8). *Choices made by the assistant, easy to change:* admins edit every parish (the brief did not say); an admin cannot demote another admin.
- **Migration from `admins/{uid}`:** the first superadmin's old `admins/{uid}` record (`role: superadmin`) still counts in the rules **only while that person has no `users/{uid}` profile**; at their next sign-in the app creates the profile with role `superadmin` (the create rule allows exactly that). `admins` is now read-only. `parish-admin` no longer exists (nobody had it). Delete the `admins` collection in the console once the profile exists, and later remove `legacySuper()` from the rules: while it exists, a superadmin whose profile is deleted regains superadmin through it. A superadmin can demote or delete another superadmin (two can leave none): recover in the console. An independent review of the rules (23 Nov 2026) found no escalation path for a non-admin; it could not run them either.
- **Deleting a user deletes only the profile** (role, later favourites). The Google/email sign-in account stays and the person starts again as `user` at their next sign-in. A real account delete or disable needs the Admin SDK, i.e. a Cloud Function (not built; the brief's SuperAdmin "delete users" is met in this limited sense). Role changes take effect on the person's next page load, not instantly.
- **24 Nov 2026 changes:** (1) the first page heading is just **Services** / **Ακολουθίες** (Sacred Mysteries are organised individually, not scheduled; `servicesHeading` in `i18n.ts`). (2) After signing in, **everybody goes to the first page** (`/` → `/services`), never to My page; "My page" is one click away in the menu for admins. The sign-in page now only shows a notice when the profile could not be loaded. (3) **How each person signs in** is stored on the profile as `providers` (`['google']`, `['password']` or both, from Firebase `providerData`, `src/lib/signIn.ts`) and shown on the Users page as "Signs in with": Google / Email / Email + Google / Unknown (older profiles fill it in at their next sign-in). Firebase only reveals providers to the person themselves, hence the copy; the rules allow only `google` and `password` there. **Rules changed again: deploy `firestore.rules` before the app** (a new person's first profile is refused by the old rules).

The function needs the **Blaze plan**; logic is in `functions/src/checkEmailLogic.ts` (tested, `tests/check-email.test.ts`); not run against real Firebase from this sandbox. Admins and superadmins (role hint, display only) see an **Add parish** button on the public Parishes page and an **Edit** link on each parish; both open `ParishesAdminPage.tsx` at `/admin/parishes/new` and `/admin/parishes/:id` (`/admin/parishes` redirects to `/parishes`). The public page shows photo, city/state, description, address and a "View on map" link in the chosen language. **Rules:** `parishes` create, update and delete for admin and superadmin, shape checked by `parishOk` (a test compares what the app writes with its field list; the document id is never written as a field). `storage.rules` `parishes/{id}/{file}`: public read, admin-only write/delete (JPEG under 3 MB) via `firestore.get` of the person's profile; the first `firebase deploy --only storage` may ask to let Storage read Firestore: say yes. **Deploy `firestore:rules,storage` before the app.**

The browser tab title in `index.html` matches. Checked in Chromium at 1280 and 390 px wide, English and Greek.
- **Services schedule, stage 1 (25 Nov 2026): List and Calendar views and the Greek calendar engine.** `/services` is now a month view (`?month=YYYY-MM`, default this month in NZ time; `?view=calendar`, default list; plus the existing `?group=` / `?parish=`). **List** (`ServiceList.tsx`): one row per day that has a posted schedule (toggle "Show all days"), date, weekday, feast, NZ holiday, fast icon, and each parish's text (parish names shown unless a single parish is chosen, times in bold); **Copy** puts an HTML table (Word-friendly, entries escaped, `scheduleExport.ts`) and plain text on the clipboard. **Calendar** (`ServiceCalendar.tsx`): Monday-first grid, day colours (Pascha, Holy Week, Bright Week, Palm Sunday/Pentecost, Nativity, great feasts, Sundays), fast icon top-left, red corner for NZ public holidays, church icon for days with a posted schedule, click a day for a panel (feast, tone, fast and season, national day, posted schedule), legends. ## 7. Traps already hit (do not repeat)
- **Never define a component inside another component** (inputs lose focus on every keystroke): use module-level components.
- **Never import `firebaseAdmin.ts` or `AuthContext` from public code** (a dynamic `import('../admin/signOut')` on click is the one allowed route; it builds to its own tiny chunk). It would pull `firebase/auth` into every visitor's bundle.
- Adding a field to a parish, group or service means touching **five places**: the type in `lib/firestore.ts`, the editor form (when it exists), `firestore.rules` (when it validates fields), the README data model, and the tests.
- **Firestore's `in` operator takes at most 30 values.** `subscribeUpcomingServices` takes the first 30 parish ids of a group and drops the rest silently. Fine for a country this size; if a group could exceed 30, split into several queries.
- **The Firestore location is permanent** once the database is created. Decide it before clicking Create.
- **The Services page needs two composite indexes** (`date,time` and `parishId,date,time`), listed in `firestore.indexes.json`. Until `firebase deploy --only firestore:indexes` has been run, the queries fail with a "requires an index" error in the console.
- In tests, **`getByText(/Holy Trinity/)` also matches the parish `<option>` in the drop-down**. Match the service row text (`/Holy Trinity, Wellington —/`) instead.
- Tests must not depend on the clock: pass a fixed `Date` to `todayNZ`, and use fixed dates in services. Date text checks use loose regexes because ICU output (`Sun, 6 Dec` vs `Sun 6 Dec`) varies between Node versions.
- `npm install` prints `EBADENGINE` warnings for some `@firebase/*` packages on Node 22. They are harmless so far; Node 24 removes them.
- **`public/favicon.svg` and `public/icons.svg` are still the Vite template's.** Replace them before launch.
- The **fonts** come from Google Fonts. In an offline or sandboxed browser the page falls back to a generic serif, so screenshots there do not show the real typography.
- The assistant's container shell is `sh`; use `bash` scripts for anything with `<( )`, and wrap long commands in `timeout`.
- A static check of `firestore.rules` is not a rules test. Do not claim the rules are verified until emulator tests exist.

## 10a. Firebase setup: checklist for the next thread

**What the developer brings to the thread:** the Firebase project id, the Firestore location they chose, and the web-app config values (`apiKey`, `authDomain`, `projectId`, `storageBucket`, `messagingSenderId`, `appId`; these are public and safe to paste). **Never paste** passwords, service-account JSON or private keys; nothing here needs them. **Before starting, know these (they cost time if hit blind):**
- **Do not run `firebase init` over this repo.** It offers to overwrite `firebase.json`, `firestore.rules` and `firestore.indexes.json`, which are already correct. Instead: `npm i -g firebase-tools`, `firebase login`, then put the project id in `.firebaserc` (or `firebase use --add`).
- **`firebase.json` also lists Storage rules.** Storage now holds profile photos (`avatars/`); deploy with `firebase deploy --only storage`. Deploy with `--only`, never a bare `firebase deploy`: `firebase deploy --only firestore:rules,firestore:indexes` and later `--only hosting`. Check the current Storage requirements in the console before ever enabling it.
- **The Firestore location is permanent.** Examples near New Zealand: Sydney `australia-southeast1`, Melbourne `australia-southeast2`; confirm the current list in the console. If the console asks for an edition or a mode, choose Firestore Standard, native mode, **production mode** (the repo's rules are deployed straight afterwards).
- **`VITE_*` values are baked in at build time.** After editing `.env.local`, restart `npm run dev`; before deploying, run `npm run build` again.
- PowerShell: `copy .env.example .env.local`. `.env.local` is git-ignored; never commit it.
- Documents created by hand in the console must **not** contain an `id` field (the code does `{ id: doc.id, ...data }`, so a stored `id` would override the document id). Types matter: `order` is a number, `visible` a boolean, `date`/`time` are text.
